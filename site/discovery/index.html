How nshm Modules Are Defined, Discovered & Verified on nsh 0.7.1

Methodology Overview

Inspection of crates/nsh-cli/src/nshm/manifest.rs (Manifest::read), crates/nsh-cli/src/rust_app.rs (specifier_of), official nsh.dev/docs/nshm specs, and live nsh add executions in clean scratch apps against nsh 0.7.1 (f78eace) shows that crates.io keywords (keywords = ["nshm"]) and nsh- crate name prefixes do NOT make a package installable.

Because nsh 0.7.1 includes no built-in package search or directory listing subcommand (nsh --help only accepts explicit crate names, github:owner/repo, Git URLs, or --path), automated catalog curation in scripts/discover.mjs must combine six independent upstream channels and verify manifests statically and empirically.

1. Four Structural Manifest Kinds Accepted by nsh add

An installable nshm must satisfy both structural manifest criteria AND NSH semver compatibility (check_nsh) against the installed CLI version (0.7.1):

Rust nshmCargo.toml ([package])#[native_module("<specifier>")] attribute on a line in [lib] path (defaults to src/lib.rs)Checks nsh-core in [dependencies] (or [workspace.dependencies] via nsh-core.workspace = true) and optional nsh.json "nsh"

Hybrid nshm (Rust + TSX)Cargo.toml + nsh.json#[native_module("<specifier>")] in Rust crate + "exports" in nsh.json (matching [package] name & version if repeated; export specifiers must not collide with the Rust module specifier)Checks both Cargo.toml nsh-core and nsh.json "nsh"
Platform nshmCargo.toml + nsh.jsonnsh.json declares "platform": "<target>" + crate builds binary nsh-platform-<target> (#[native_module] optional)Checks Cargo.toml nsh-core and nsh.json "nsh"
  • An app's nsh.json is ignored when Cargo.toml is present unless nsh.json declares "exports" or "platform".
  • A Cargo.toml virtual workspace root fails nsh add with Cargo.toml has no [package] name (observed directly on github:SuperNSH/biometrics). Multi-crate repositories must publish sub-crates to crates.io or place the nshm [package] at the repo root (SuperNSH/webgpu, SuperNSH/skia, SuperNSH/widgets, SuperNSH/icons).
  • End-user NSH apps in mixed Rust+TSX mode (huacnlee/spotish, ryujane/Ferrix, SuperNSH/starter) look structurally similar because they also write #[native_module("...")] in src/lib.rs, yet set publish = false and "root"/"id" instead of "exports" in nsh.json—so curation must separate them into templates or apps.

2. The Cargo Publish Normalization Parser Quirk in nsh-cli 0.7.1

When cargo publish packages a crate tarball, Cargo rewrites inline [dependencies] nsh-core = "0.6.0" into a TOML sub-table ([dependencies.nsh-core] version = "0.6.0"). Because manifest.rs::nsh_core_requirement in nsh-cli 0.7.1 only scans the [dependencies] and [workspace.dependencies] tables, it sees None for normalized nsh-core entries. Consequently, 18 crates.io packages pinned to nsh-core 0.6 / 0.6.0 (17 SuperNSH/* 0.1.0/0.0.1 crates plus nsh-platform-miniprogram@0.1.0) pass nsh add on nsh 0.7.1 purely due to parser omission, whereas identical GitHub checkouts with un-normalized [dependencies] nsh-core = "0.6" are rejected by check_nsh. Awesome NSH treats those 18 crates as targeting NSH 0.6 until updated to 0.7 on crates.io.

[dependencies.nsh-core]
version = "0.6.0"
