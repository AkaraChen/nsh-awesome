What is Native Shell (nsh) and nshm?

Native Shell (nsh) is a Rust-first cross-platform framework where apps built in TSX or Rust render through native platform backends across desktop, mobile, GPUI, terminal, and web. Installable extensions, called nshm modules, plug into apps via nsh add. Awesome NSH curates verified nsh 0.7.1 packages, core crates, templates, and docs with index.json.

Supply-Chain & Build Permission Notice

Installing a Rust, hybrid, or platform nshm runs its build.rs build script, procedural macros, and runtime code with your application's full local and runtime permissions. Crates can also contribute OS permissions, Info.plist descriptions, macOS entitlements, and HarmonyOS module entries through [package.metadata.nsh]. Review upstream source repositories and nsh.lock diffs before shipping any dependency.

Frequently Asked Questions About Native Shell & nshm

How do built-in nsh/* modules, installable nshm packages, and official framework crates differ?

Built-in runtime modules imported from "nsh" ship directly inside the Native Shell engine and require no installation. Installable nshm modules are third-party or optional first-party packages added to nsh.json and nsh.lock with nsh add. Official framework crates like nsh-core, nsh-base, and nsh-platform-macos live inside longbridge/nsh, lack #[native_module] or nsh.json exports, and cannot be added with nsh add—either nsh manages them automatically or Rust applications depend on them via cargo add.

Why does nsh 0.7.1 not provide a built-in nsh search command?

In nsh 0.7.1, the CLI focuses on explicit package coordinates: crate names on crates.io, github:owner/repo shorthands, Git URLs with optional --rev/--tag/--branch flags, and local --path directories. There is no central package registry index built into the CLI, which is why Awesome NSH runs six-channel discovery and publishes both human pages and index.json.

Why do 6 of the 13 verified nshm packages install from GitHub or a Git URL instead of crates.io?

Several fast-moving 0.7 packages remain pinned to GitHub or Git URLs in this catalog: nsh-webgpu and nsh-skia explicitly set publish = false in Cargo.toml, pure-TSX nsh-query has no Cargo.toml, early-stage 0.1.0 nsh-shadcn was verified via github:caoxing9/nsh-shadcn on 2026-11-26 prior to its initial 2026-11-27 crates.io upload, nsh-platform-harmonyos 0.1.0 on crates.io predated the "platform" manifest field required by nsh add (fixed in GitHub 0.1.1), and nsh-widgets 0.4.1 on crates.io and tag v0.4.1 still pins nsh: ^0.6 while its master branch updates to ^0.7.1.

Do all nshm packages require a Rust toolchain during app builds?

No—only packages backed by Rust crates (rust-nshm, hybrid-nshm, and platform-nshm) require Cargo and rustc when building native hosts, plus wasm32-unknown-unknown (and sometimes LLVM clang/llvm-ar) for web builds. Pure TSX packages such as nsh-query have no Cargo.toml and ship TypeScript source bundled directly by nsh.

What does Awesome NSH verification test—and what does it not test?

Automated CI runs nsh add ... for every installable entry inside a clean scratch nsh.json app on nsh 0.7.1, confirming manifest resolution and nsh.lock generation. It does NOT compile native binaries across physical iOS, Android, macOS, Windows, Linux, or HarmonyOS hardware, nor does it run upstream runtime UI test suites.
