系统梳理 Awesome NSH 基于 longbridge/nsh 源码与 nsh 0.7.1 (f78eace) 真机命令行实测的发现方法：四类合法清单形态、Cargo 0.6 规范化 parser quirk、六渠道命中数与完整拒收账本。

调研背景与源码依据

直接审阅 longbridge/nsh 中的 crates/nsh-cli/src/nshm/manifest.rs（Manifest::read）、crates/nsh-cli/src/rust_app.rs（specifier_of）、官方 nsh.dev/docs/nshm 文档并在独立临时应用中执行 nsh add 后可以确认：**crates.io 上的 keywords = ["nshm"] 或 nsh- 命名前缀并不能让包具备安装资格**。

由于 nsh 0.7.1 CLI 本身未内置包搜索或列出目录子命令（nsh add 仅支持显式 crate 名、github:owner/repo、Git URL 或 --path），Awesome NSH 的 scripts/discover.mjs 通过整合六条外部发现渠道，再结合清单静态分析与真实 nsh add 命令给出可复现结果。

一、`nsh add` 认可的四种合法 nshm 清单结构

一个包必须同时满足下方“结构入场规则”与“NSH 语义化版本校验（check_nsh）”，才能被 nsh 0.7.1 正常添加：

模块形态必备清单文件结构入口判断标准NSH 版本兼容检查（check_nsh）
Rust nshmCargo.toml ([package])[lib] path（默认 src/lib.rs）某行包含 #[native_module("<specifier>")] 属性宏检查 [dependencies]（或通过 nsh-core.workspace = true 引用 [workspace.dependencies]）中的 nsh-core 及可选 nsh.json "nsh"
TSX nshmnsh.json（无 Cargo.toml）声明 "name"、semver "version"，且非空 "exports" 将 <name> 或 <name>/* 映射到真实存在的 TSX/TS 文件检查可选 "nsh" semver 要求
Hybrid nshm（Rust + TSX）Cargo.toml + nsh.jsonRust crate 导出 #[native_module("<specifier>")] 且 nsh.json 声明 "exports"（若重复写 name/version 须与 Cargo 一致，且导出名不可与 Rust specifier 碰撞）同时校验 Cargo.toml 的 nsh-core 与 nsh.json 的 "nsh"
Platform nshmCargo.toml + nsh.jsonnsh.json 声明 "platform": "<target>" 且 crate 构建二进制 nsh-platform-<target>（#[native_module] 可选）同时校验 Cargo.toml 的 nsh-core 与 nsh.json 的 "nsh"
  • 存在 Cargo.toml 时，除非 nsh.json 显式声明了 "exports" 或 "platform"，否则 nsh.json 会被判定为普通应用配置而忽略。
  • Cargo.toml 为虚拟工作区（virtual workspace root）会在 nsh add 时直接报错 Cargo.toml has no [package] name（实测见于 github:SuperNSH/biometrics）。多 crate 仓库必须把子 crate 发布到 crates.io，或将主 nshm [package] 放到仓库根目录（如 SuperNSH/webgpu、SuperNSH/skia、SuperNSH/widgets、SuperNSH/icons）。
  • 采用混合模式的终端用户应用（如 huacnlee/spotish、ryujane/Ferrix、SuperNSH/starter）在 src/lib.rs 中同样写了 #[native_module("...")]，结构极易混淆，但它们在 Cargo.toml 标注 publish = false 并在 nsh.json 声明 "root"/"id" 而非 "exports"，需人工/规则筛除。

二、发现 `nsh-cli 0.7.1` 中 Cargo 发布规范化解析绕过现象

当开发者运行 cargo publish 打包上传 crate 时，Cargo 会把平写形式 [dependencies] nsh-core = "0.6.0" 规范化改写成 TOML 子表（如 [dependencies.nsh-core] version = "0.6.0"）。然而 nsh-cli 0.7.1 的 manifest.rs::nsh_core_requirement 只扫描 [dependencies] 与 [workspace.dependencies]，遇到子表形式会误判 nsh-core 约束为 None。因此 crates.io 上 **18 个仍锁定 nsh-core 0.6 / 0.6.0 的 crate**（17 个 SuperNSH/* 0.1.0/0.0.1 包及 nsh-platform-miniprogram@0.1.0）在 nsh 0.7.1 下竟然能绕过检查；而同样的源码从 GitHub 拉取未规范化写法时则会立刻被 check_nsh 拒绝。Awesome NSH 坚持按真实约束将其归为 0.6 目标暂缓收录。

[dependencies.nsh-core]
version = "0.6.0"
