板块概述

在 crates.io 查询 nsh-core 的反向依赖（共返回 107 条结果，其中包含 18 个依赖它的官方框架 crate）时，新手常把官方框架全部 19 个内部 crate 误认为可用 nsh add 安装的模块。需要明确的是：**本分区列出的 19 个 Apache-2.0 crate 全都不是 nshm**，直接运行 nsh add nsh-core 或 nsh add nsh-base 会在 nsh 0.7.1 立即报错 no #[native_module("...")] at the crate's root。

在 Native Shell 0.7.1 架构中，TSX 或纯 Rust 应用构建宿主时由 nsh CLI 自动管理并链接这些 crate；若编写纯 Rust 应用或开发 nshm 扩展库，则直接在 Cargo.toml 中通过 cargo add 声明依赖，而非写入 nsh.json 的扩展列表。

为什么 `nsh add` 会拒绝全部 19 个官方框架 crate？

nsh-cli 的清单校验器（crates/nsh-cli/src/nshm/manifest.rs）要求可安装包必须在库入口包含 #[native_module("<specifier>")] 宏、提供含 "exports" 的纯 TSX nsh.json，或在 nsh.json 中声明 "platform" 目标标识及对应 nsh-platform-<target> 二进制。诸如 nsh-core 与 nsh-base 提供的是 Rust 核心 trait、影子树、布局引擎与无样式交互行为，并不导出 JS/TSX 模块桥；官方 8 大平台后端则内建于 nsh 构建管线，只有像 nsh-platform-harmonyos 这样的社区扩展后端才走 "platform" nshm 机制。

常见排查与使用误区说明

区分 nsh-base（0.7.1）与带样式 UI 组件库

nsh-base 负责焦点管理、键盘导航、弹窗、代码编辑器与无障碍逻辑，是 nsh-omarchy 和 nsh-shadcn 共同依赖的基础行为层；TSX 应用直接从框架导入 nsh/base 能力，而非执行 nsh add nsh-base。

区分官方后端与社区 "platform" nshm

8 个官方 nsh-platform-* 随 longbridge/nsh 统一发版；只有基于 NSH 公共平台扩展点开发的第三方目标（例如 nsh-platform-harmonyos）才会以 "platform" nshm 形式供 nsh add 安装。

为什么同源仓库里的 nsh-extra（0.7.1）归入 /zh/nshm/

nsh-extra 虽然也在 longbridge/nsh 仓库维护，但它的根文件 crates/nsh-extra/src/lib.rs 声明了 #[native_module("nsh-extra")]，专门供应用按需通过 nsh add nsh-extra --features ... 启用相机、定位等系统权限能力。
