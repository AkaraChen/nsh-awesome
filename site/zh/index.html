什么是 Native Shell（nsh）与 nshm 模块？

Native Shell（nsh）是以 Rust 为核心的跨平台原生 UI 框架，开发者用 TSX 或 Rust 编写界面，即可在桌面、移动端、GPUI、终端与 Web 上挂载原生视图。可通过 nsh add 安装的扩展包称为 nshm。Awesome NSH 基于 nsh 0.7.1 实测收录 13 个 nshm、19 个框架 crate、模板与教程，并提供 index.json。

nsh 0.7.1 三种远程安装来源对比

nsh 0.7.1 命令行支持 crates.io、github:owner/repo 与 Git URL 三种远程来源及本地 --path 路径。不同来源对应的锁文件格式与维护背景各有差异。

Native Shell 与 nshm 常见问题

内置模块 nsh/*、可安装 nshm 与官方框架 crate 有何区别？

从 "nsh" 导入的内置模块随运行时附带，无需额外安装；nshm 是通过 nsh add 写入 nsh.json 与 nsh.lock 的第三方或可选扩展模块；而 nsh-core、nsh-base、nsh-platform-macos 等 19 个官方 crate 属于框架内部组件，缺少 #[native_module] 与 exports，不能执行 nsh add，由 nsh 自动管理或在 Rust 项目中用 cargo add 引入。

为什么 nsh 0.7.1 没有内置 nsh search 命令？

nsh 0.7.1 的命令行聚焦于从明确标识安装模块：crates.io crate 名、github:owner/repo 简写、带分支/修订号的 Git URL 或本地 --path，暂未提供中央包搜索接口。因此本站点通过自动化脚本汇总六大渠道并开放 index.json 供人与 AI 工具检索。

为何 13 个已验证模块中有 6 个通过 GitHub 或 Git URL 安装？

0.7 生态尚处快速迭代阶段：nsh-webgpu 与 nsh-skia 在 Cargo.toml 中标明了 publish = false；纯 TSX 的 nsh-query 不含 Cargo.toml；早期 0.1.0 版本的 nsh-shadcn 于 2026-11-26 验证时尚未发布至 crates.io（初始 0.1.0 于 2026-11-27 上传），当前目录仍保留已验证的 github:caoxing9/nsh-shadcn 安装指令；nsh-platform-harmonyos 在 crates.io 的 0.1.0 缺少 "platform" 字段导致 nsh add 报错，必须装 GitHub 0.1.1；nsh-widgets 的 crates.io 0.4.1 与 tag v0.4.1 仍锁定 nsh: ^0.6，需要用 --rev master 安装。

所有 nshm 模块在打包应用时都需要安装 Rust 工具链吗？

不一定。包含 Rust crate 的 rust-nshm、hybrid-nshm 与 platform-nshm 需要本地 Cargo 与 rustc（Web 目标通常还需 wasm32-unknown-unknown，部分图形库还需 LLVM clang/llvm-ar）；而像 nsh-query 这样的纯 TSX 模块不含 Cargo.toml，可直接由 nsh 打包。

Awesome NSH 的自动验证具体测了什么、没测什么？

仓库 CI 会在全新临时应用的 nsh.json 目录下使用 nsh 0.7.1 逐条运行 nsh add 并校验 nsh.lock 生成结果。它没有在真机或全平台环境下实际编译与运行 UI 界面，原生运行验证边界已在 /zh/about/ 页面明确说明。
